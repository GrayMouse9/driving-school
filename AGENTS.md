# AGENTS.md — общие правила работы над проектом

Этот файл содержит общие инструкции для всех участников и хранится в корне
репозитория. Личные настройки агентов и параметры конкретного компьютера
не добавлять в командные файлы.

## Проект и источники информации

Браузерный многопользовательский тренажёр ПДД. Клиент: TypeScript, Vite и three.js,
без React. Сервер: Go, HTTP/WebSocket и PostgreSQL. Один серверный компьютер
раздаёт frontend и данные; другим ноутбукам нужен только браузер.

Перед изменениями проверять актуальный код, состояние Git и документы:

- `README.md` — структура проекта, запуск и проверки.
- `docs/requirements.md` — требования и согласованные решения команды.
- `docs/architecture.md` — архитектура и границы компонентов.
- `docs/api-contracts.md` — фактический HTTP/WS-контракт.
- `docs/setup.md` — окружение, PostgreSQL и локальная сеть.
- `docs/scenarios.md` — подготовленный учебный контент.

Требования определяют цель продукта, архитектура — устройство системы,
этот файл — правила работы. Наличие описания, типов или пустой папки
не означает, что функция реализована. При существенном противоречии между
заданием, документами и кодом сообщить о нём до спорных изменений.

## Объём задачи и согласование

- Реализовывать только запрошенное. Не добавлять новые требования и функции
  и не исправлять несвязанные ошибки по собственной инициативе.
- Сохранять изменения других участников. Перед редактированием читать файл
  и проверять текущий diff; не откатывать чужие правки.
- Не проводить посторонний рефакторинг, переименования и форматирование.
  Изменять связанные файлы только в объёме, необходимом для задачи.
- Существенные изменения архитектуры, API, форматов данных, технологий,
  зависимостей и сервисов вне согласованной задачи сначала предложить:
  объяснить причину, последствия и дождаться решения.
- Прямое поручение на изменение считается согласованием соответствующего
  объёма работы. Не запрашивать повторное разрешение на уже порученное.
- Перед крупной задачей кратко описать шаги и затронутые компоненты в чате.
  Небольшие однозначные изменения выполнять без дополнительного согласования.

## Документация и ответы

- Ответы и объяснения давать в чате. Не оформлять ответ отдельным файлом
  без прямой просьбы сохранить его в файл.
- Не создавать и не изменять `.md`-файлы без прямой просьбы. Поручение изменить
  код само по себе не разрешает правки README, документации, планов или инструкций.
- Документация находится в `docs/`, общая точка входа — корневой `README.md`.
  Обновлять существующий документ по теме, не создавать дубли.
- Если отдельно запрошены новые спецификации или планы, сохранять их внутри
  `docs/superpowers/`. Пользовательские указания о конкретном пути имеют приоритет.
- Описывать проверенное состояние точно: отличать реализованный код, целевые
  требования, подготовленные типы и ещё не подключённые компоненты.

## Реализация и безопасность

- Следовать существующему стилю. Выбирать простое решение без лишних
  абстракций, сервисов и зависимостей.
- Не выдавать заглушки, фикстуры и TODO за готовую функцию.
- Обрабатывать ошибки явно. Не отключать авторизацию, валидацию и проверки
  доступа ради удобства реализации.
- Не хранить реальные пароли, токены и другие секреты в коде или документации.
- UI использует существующие Network и GameScene; не создавать второй
  WebSocket для интерфейса.
- Движение и результаты обучения определяет сервер; клиент отображает состояние.
  Полный мир не включать в клиентскую сборку, загружать участки по позиции
  и освобождать ресурсы дальних участков.
- Соблюдать обязательные требования автономности: без CDN, внешних API
  и облачного ИИ во время игры.

## Проверки

Запускать проверки, соответствующие изменениям:

- Клиент: `npm --prefix frontend test` и `npm --prefix frontend run build`.
- Сервер: `go test ./...` и сборка из `backend/`.
- Мир: `node server-data/world/check-world.mjs --go` из корня.

Интеграционные Go-тесты требуют отдельной БД в
`DRIVING_SCHOOL_TEST_DATABASE_URL`; без неё часть тестов пропускается.
`test:browser` использует фикстуры, `test:backend` — настоящий сервер
и занимает две машины: запускать его на отдельном тестовом сервере.

Не менять ожидания тестов только ради успешного результата. Не заявлять
о работоспособности без проверки. Различать фикстуры, настоящий backend,
локальные браузерные контексты и физические ноутбуки. Учёт байтов данных
мира не называть измерением памяти GPU/RAM.

## Git и итог работы

- Перед разрешённым добавлением в Git прочитать итоговые файлы и проверить
  состав: исключить секреты, зависимости, сборки, БД и личные настройки.
- Не обходить ограничения доступа к `.git` и не применять разрушительные
  Git-команды без отдельного явного поручения.
- В результате кратко указать изменения, выполненные проверки, способ
  самостоятельной проверки и существенные ограничения. Если проверка
  недоступна, сообщить об этом; не выдавать предположение за результат.
