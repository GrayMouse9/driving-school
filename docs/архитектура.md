## 1. Что нужно решить сейчас

Предлагается подтвердить **один пакет ниже**, либо указать номер и замену.
Не реализовывать одновременно два несовместимых протокола.

| № | Предложение для v1.1 | Что отличается от прежних вариантов |
|---|---|---|
| D1 | Backend Go, авторизация PostgreSQL; все процессы на одном ноутбуке в аудитории |
| D2 | Существующий клиент `client/`: TypeScript + Vite + three.js; UI в `client/src/ui/` | React допустим для UI по согласованию; переноса всей сцены и второго клиента нет |
| D3 | Один origin, порт по умолчанию 8080, HTTP `/api/v1`, WS `/ws` | Было 3000 и `/api` без `/v1`; порт конфигурируется сервером |
| D4 | Клиент посылает **управление**, Go рассчитывает движение и коллизии | Будет `player_input`.  |
| D5 | Имена WS в snake_case, конверт `{v,type,requestId?,payload}` | Стиль Ани; точные поля определены ниже |
| D6 | Один вход в мир: WS `join_world`; отдельного HTTP `/game/session/join` нет | Устраняем два способа одного действия |
| D7 | Сервер выдаёт только метаданные ближайших разрешённых участков и их ресурсов | Полный список всех объектов/участков не загружаем в клиент |
| D8 | Локальная LLM + RAG по проверенным ПДД и JSON-сценариям; память в БД | Уточнено командой в 14:35–14:36. LLM объясняет, backend проверяет; отдельный Python-процесс — выбор Ани |


Уточнение пользователя от 14:36 принято в содержание кандидата: **четыре
задания, две роли, автобус-NPC, локальная LLM с RAG**. Это заменяет прежнюю
рекомендацию о трёх заданиях и необязательной LLM. Остальные D1–D7 остаются
на согласовании; наличие реализации и принятие контракта Аней не подразумеваются.

## 2. Обязательный результат

- Общий low-poly город, два различимых учебных автомобиля и имена водителей.
- Три одновременных браузера; серверный браузер с самого начала использует localhost.
- Камера от первого лица из салона, WASD, тормоз и остановка; игрок всегда находится в автомобиле, выход и пересадка недоступны.
- E или щелчок по знаку открывает текстовый диалог со знаком; это одно серверное действие.
  Сервер проверяет дистанцию, а UI освобождает мышь и блокирует управление на время ввода.
- Авторизация, общий чат, серверное сохранение позиции/прогресса/личной памяти.
- Четыре задания: две разные карточки в общей сцене перекрёстка (Даша П,
  Даша К и автобус-NPC, движущийся по серверной траектории, а не управляемый LLM); затем отдельный поворот с пешеходами для П и STOP для К.
  Независимые интерфейсы и маршруты после общего эпизода (§9).
- Сервер проверяет действия/ответы; клиент не назначает себе успех.
- Подгрузка по положению, освобождение дальних данных и GPU-ресурсов,
  максимум 10% уникальных данных мира, рабочий предел 8%.
- После ошибки агент меняет пример, освоенную вводную без причины не повторяет,
  неизвестный вопрос уточняет. Правила и примеры проверены по ПДД РФ;
  авторские задания не называем официальными билетами.
- Никаких обязательных внешних запросов. Все ресурсы, БД и ИИ на серверном ноутбуке.
- Два обязательных прогона: LAN с тремя браузерами; Wi-Fi сервера выключен,
  новый вход и игра через localhost продолжают работать.

Озвучка, сложные модели, зеркала и эффекты —  не реализуются.
LLM с RAG включена в согласуемый демонстрационный сценарий, её запуск нужно проверить.

## 3. Общие типы и семантика

Следующие TypeScript-записи описывают JSON, не требуют TypeScript на сервере.
`Id` — непустая строка, `number` — конечное число; никаких NaN/Infinity.
Позиции абсолютные, метры, Y вверх, движение в XZ, yaw в радианах,
yaw=0 смотрит вдоль -Z; положительный steer поворачивает влево.
Взгляд водителя направлен вперёд; мышь не меняет направление взгляда или автомобиля.
Автомобиль поворачивается клавишами A/D; управление осуществляется с клавиатуры.
Скорость существует в симуляции, но её показатель не отображается на экране.

```ts
type Id = string;
type Vec3 = { x: number; y: number; z: number };
type User = { id: Id; username: string };
type Player = {
  id: Id; username: string; position: Vec3; yaw: number;
  vehicleId: Id;
};
type Vehicle = {
  id: Id; driverId: Id | null; variant: 'blue' | 'green' | 'yellow' | 'bus';
  controller: 'player' | 'npc';
  position: Vec3; yaw: number; speed: number;
};
type Progress = {
  lessons: { lessonId: Id; status: 'available' | 'active' | 'completed'; attempts: number }[];
  learnedTopics: string[];
  mistakes: { topic: string; kind: 'answer' | 'driving'; count: number }[];
};
type Envelope<T> = { v: 1; type: string; requestId?: string; payload: T };
```

У игрока всегда есть vehicleId и совпадающий driverId его автомобиля.
Сервер назначает идентификаторы и берёт пользователя из cookie.
Входящие playerId, progress, координаты в командах управления не принимаются.

## 5. HTTP API

Все пути относительные. Cookie: HttpOnly, SameSite=Lax либо Strict;
Secure при HTTPS; Path=/; срок действия и отзыв проверяются сервером.
В автономной доверенной LAN HTTP допустим. Пароли хешируются Argon2id.
Тело POST — JSON. Ошибка во всех HTTP-ручках:
`{"error":{"code":"UNAUTHENTICATED","message":"Войдите в аккаунт"}}`.

| Метод | Путь | Тело запроса | Успех |
|---|---|---|---|
| POST | `/api/v1/auth/register` | `{username,password}` | 201 `{user:User}`; автоматически не входит |
| POST | `/api/v1/auth/login` | `{username,password}` | 200 `{user:User}` + session cookie |
| POST | `/api/v1/auth/logout` | `{}` | 204 без тела; cookie/сессия отозваны, её WS закрыты |
| GET | `/api/v1/profile` | — | 200 `{user:User,progress:Progress}` |
| GET | `/api/v1/game/session` | — | 200 `{id:'main',playersOnline:number,maxPlayers:number}` |
| GET | `/api/v1/world/manifest` | — | 200 `WorldMeta`, только после входа в мир |
| GET | `/api/v1/world/chunks/{chunkId}` | — | 200 `Chunk`, только разрешённый текущей позицией |
| GET | `/api/v1/world/assets/{assetId}` | — | Байты разрешённого ресурса; в MVP без внешних моделей не вызывается |
| GET | `/api/v1/progress` | — | 200 `{progress:Progress}` |
| GET | `/api/v1/health` | — | 200 `{status:'ok'}` либо 503 `{status:'degraded'}`; без секретов |

Кроме register/login/health всё требует сессии. Участки/ресурсы также требуют
входа в мир и права доступа по подтверждённой серверной позиции.
401 — нет сессии; 403 — нет доступа/вне зоны; 404 — неизвестный объект;
409 — занятое имя/машина; 400 — неверные поля; 429 — превышение частоты;
503 — временно недоступный сервис. Неверный пароль: 401 INVALID_CREDENTIALS.
Username: 1–40 символов после trim, регистр при проверке уникальности не учитывается.
Пароль: 8–15 символов, не trim. Проверки повторяются на сервере.

JSON-поля всех успешных ответов выше обязательны. Для /api/v1/profile без пройденных
уроков возвращается Progress с пустыми массивами. Прогресс не передаётся
как массив в одном ответе и объект в другом.

## 6. Подключение, WS и переподключение

1. Регистрация при необходимости → login → GET /api/v1/profile.
2. Только после успешной проверки сессии создаётся WS:
   `(location.protocol === 'https:' ? 'wss://' : 'ws://') + location.host + '/ws'`.
3. Сервер проверяет cookie и Origin **до Upgrade**, без сессии HTTP 401.
4. После открытия клиент посылает join_world с requestId. До world_joined
   управление и остальные игровые команды заблокированы.
5. Сервер отвечает world_joined, затем world_interest и players_snapshot.
   HTTP world/manifest уже доступен после world_joined.
6. При разрыве/выходе отменяются запросы мира и новые игровые команды;
   нулевой ввод назначается сервером, а не зависит от последнего пакета клиента.
7. Кнопка переподключения заново проверяет /api/v1/profile и выполняет join_world.
   Повторные клики/поздние ответы не создают дополнительные WS и сцены.
8. Logout закрывает WS и очищает локальные данные мира и персональный UI.

У пользователя одно активное игровое соединение: новый join_world заменяет
старое (старый WS закрывается 4001 SESSION_REPLACED). Для трёх браузеров нужны
три разных аккаунта. Не допускаем двух водителей одной машины.
Повторный join_world на том же соединении возвращает текущее состояние,
не создавая нового игрока. Сервер сразу прекращает ввод отключённого игрока,
освобождает машину через 10 секунд; активный disconnected игрок удаляется
из снимков после этого тайм-аута. После истечения сессии WS закрывается 4003.

requestId обязателен всем клиентским событиям кроме player_input и ping.
Ответы на операции, включая ошибки, повторяют requestId; broadcast его не содержит.
Одинаковый requestId операции в течение сессии не выполняет её повторно:
сервер возвращает прежний ответ. Клиент не перепосылает операции автоматически
после переподключения, а сначала получает восстановленное состояние.
Начальные лимиты: сообщение 16 KiB UTF-8; input 20/с, чат 2/с,
вопрос знаку 1/с; излишек отклоняется RATE_LIMITED. Heartbeat ping раз в 10 с,
при отсутствии ответа 30 с соединение считается потерянным.

### Клиент → сервер: точные payload

| type | payload | Ответ |
|---|---|---|
| `join_world` | `{}` | `world_joined` |
| `leave_world` | `{}` | `world_left` |
| `world_loaded` | `{revision,chunkIds}` | `world_load_status` |
| `world_load_failed` | `{revision,code,chunkId,message}` | `world_load_status` и восстановление по §8 |
| `player_input` | `{seq,throttle,brake,steer}` | Подтверждение seq в snapshot |
| `chat_send` | `{text}` | `action_result` и broadcast `chat_message` |
| `interact` | `{objectId}` | `interaction_result` |
| `npc_message` | `{npcId,text,taskId?,sceneRevision?}` | `npc_reply`; необязательный `npc_typing` |
| `episode_join` | `{scenarioId:'shared-priority',role:'P'|'K'}` | Персональный `episode_state` |
| `episode_ready` | `{episodeId,sceneRevision}` | `action_result`, затем `episode_state` |
| `episode_leave` | `{episodeId}` | `action_result`, прогресс не начисляется |
| `lesson_start` | `{lessonId}` | `task_started` |
| `answer_submit` | `{taskId,answerId,sceneRevision}` | `answer_result` |
| `ping` | `{clientTime}` | `pong` |

seq — возрастающее целое на WS; старые seq игнорируются. throttle/brake: 0..1,
steer: -1..1. Взгляд водителя направлен вперёд. W/S — газ/тормоз;
A/D — поворот. Мышь не управляет автомобилем или направлением взгляда.

### Сервер → клиент: точные payload

```ts
type WorldJoined = {
  selfId: Id; tickRate: 20; player: Player; vehicles: Vehicle[]; progress: Progress;
  episode: EpisodeState | null; activeTask: TaskStarted | null;
};
type Snapshot = {
  tick: number; serverTime: number; ackInputSeq: number;
  players: Player[]; vehicles: Vehicle[];
  pedestrians: PedestrianState[]; signals: SignalState[];
};
type ActionResult = { action: 'chat_send' | 'episode_ready' | 'episode_leave'; ok: true };
type ChatMessage = { senderId: Id; username: string; text: string; serverTime: number };
type InteractionResult = {
  objectId: Id; npcId: Id | null; name: string;
  text: string; lessonIds: Id[];
};
type NpcReply = {
  npcId: Id; name: string; text: string; topic: string | null;
  exampleId: Id | null; suggestedQuestions: string[];
  taskId: Id | null; sceneRevision: number | null;
  sources: { id: Id; pddPoints: string[] }[]; visualHints: VisualHint[];
  generation: 'local_llm';
};
type TaskStarted = {
  lessonId: Id; taskId: Id; kind: 'choice' | 'driving'; title: string; prompt: string;
  scenarioId: Id; episodeId: Id | null; sceneRevision: number; role: 'P' | 'K';
  sourceLabel: string; helperNpcId: Id;
  options: { id: Id; text: string }[];
};
type AnswerResult = {
  lessonId: Id; taskId: Id; correct: boolean; explanation: string;
  stage: 'choice' | 'driving'; mistakeKind: 'answer' | 'driving' | null;
  nextTaskId: Id | null;
};
type WorldLoadStatus = { revision: number; ready: boolean };
type ServerError = { code: string; message: string; retryable: boolean };
```

| type | payload |
|---|---|
| `world_joined` | WorldJoined, с requestId join_world |
| `world_left` | `{}`, с requestId; соединение остаётся только для повторного входа |
| `players_snapshot` | Snapshot, без requestId; включает автобус, пешеходов и сигналы |
| `episode_state` | EpisodeState (§9), персональный push; с requestId для episode_join |
| `world_interest` | WorldInterest (§8), без requestId |
| `world_load_status` | WorldLoadStatus, с requestId world_loaded/world_load_failed |
| `action_result` | ActionResult, с requestId |
| `chat_message` | ChatMessage, broadcast |
| `interaction_result` | InteractionResult, с requestId |
| `npc_typing` | `{npcId}`, с requestId исходного вопроса |
| `npc_reply` | NpcReply, с requestId |
| `task_started` | TaskStarted; с requestId для lesson_start, иначе push без requestId |
| `answer_result` | AnswerResult; с requestId для answer_submit, иначе push без requestId |
| `progress_updated` | `{progress:Progress}`, персональный push |
| `server_error` | ServerError, requestId при ошибке операции |
| `pong` | `{clientTime,serverTime}`, эхо clientTime из ping |

Snapshot полностью заменяет список сущностей в области видимости, всегда
содержит собственного игрока и его машину. Отсутствующие удаляются клиентом.
Старые tick игнорируются; после world_joined счётчик начинается заново.
Снимки 10/с, симуляция 20/с, ввод не более 20/с, отрисовка независимо.
Дополнительные player_joined/player_left не обязательны: присутствие видно из snapshot.

Коды ошибок: UNAUTHENTICATED, INVALID_CREDENTIALS, USERNAME_TAKEN,
INVALID_MESSAGE, NOT_IN_WORLD, OUT_OF_RANGE, NOT_FOUND, VEHICLE_BUSY,
VEHICLE_MOVING, WORLD_BUDGET_EXCEEDED, STALE_WORLD_REVISION, RATE_LIMITED, AGENT_UNAVAILABLE, ROLE_BUSY, STALE_SCENE, EPISODE_NOT_READY.
Неизвестное сообщение отклоняется, сервер не трактует payload как исполняемый код.

## 8. Мир и проверяемый бюджет данных

```ts
type WorldMeta = {
  version: string; totalWorldBytes: number; cacheBudgetBytes: number;
  accounting: 'utf8-uncompressed-json-plus-unique-assets';
};
type ResourceRef = { id: Id; version: string; byteLength: number };
type ChunkRef = {
  id: Id; version: number; dataBytes: number; resources: ResourceRef[];
};
type WorldInterest = {
  revision: number; worldVersion: string;
  chunks: ChunkRef[]; removeChunkIds: Id[]; cacheBudgetBytes: number;
};
type Agent = {
  id: Id; kind: 'yield' | 'stop' | 'crosswalk' | 'priority'; position: Vec3; yaw: number;
  mainRoadArms?: ('north' | 'east' | 'south' | 'west')[];
};
type Chunk = {
  id: Id; version: number; origin: {x:number;z:number}; size: number;
  objects: {
    id: Id; kind: 'building' | 'tree'; position: Vec3; yaw: number;
    size: Vec3; color: string; collidable: boolean;
  }[];
  roads: {id:Id;position:Vec3;yaw:number;width:number;length:number}[];
  agents: Agent[];
  resources: Id[];
  teaching?: {
    paths: {id:Id;points:Vec3[]}[];
    zones: {id:Id;kind:'stop'|'conflict'|'crosswalk'|'checkpoint';outline:Vec3[]}[];
    signals: {id:Id;position:Vec3;yaw:number}[];
  };
};
```

В MVP ресурсы `[]`: окружение строится локально из простых примитивов по
полученным данным, без GLB/удалённых текстур. Если добавляются общие файлы,
сначала согласуются их формат/декодирование, серверные размеры и выгрузка.
Неподдержанный ресурс — явная ошибка, а не скрытое исключение из бюджета.
Позиции объектов абсолютные; origin задаёт границы, а не сдвиг.
Дом — параллелепипед размера size с основанием в position.y;
дерево — ствол и крона, size задаёт габарит. Дорога при yaw=0 вдоль Z,
width по X, length по Z. Столб знака в position, лицо и табличка над ним. Для общего перекрёстка
приоритет показан настоящими «Главная дорога»/«Уступите дорогу» и табличкой
направления главной; mainRoadArms — направления в мировых координатах,
рендер поворачивает диаграмму для наблюдателя, не меняя смысла.
Поле teaching содержит только видимые пути/границы/светофоры текущего участка;
оно учитывается в dataBytes. Решения/правильные ответы/правила в него не входят.
Дополнительный знак priority не заменяет трёх говорящих персонажей.
Динамическое состояние автобуса, пешеходов и сигналов идёт через snapshot,
а не через пересборку/повторную загрузку статических участков.
Отдельные знания и задания не входят в Chunk.

world_interest.chunks — **полная замена** текущего разрешённого набора,
revision строго возрастает. removeChunkIds — подсказка ранней выгрузки;
отсутствующие в chunks всё равно удаляются. Один id не может одновременно
присутствовать в chunks и removeChunkIds. Старые revision игнорируются.
Клиент не получает манифест всего города: HTTP manifest возвращает только
WorldMeta; ближайшие ChunkRef приходят в world_interest.
Разрешение и данные относятся к одной worldVersion; при смене версии
очищается старый мир и повторно получается WorldMeta. Состав chunk.resources
должен совпадать с ChunkRef.resources по id.

### Подтверждение загрузки и восстановление

После установки **всех** chunks текущей revision и их ресурсов клиент отправляет
world_loaded: `{revision,chunkIds}`; chunkIds содержит ровно весь набор id
из текущего world_interest, без дубликатов. Сервер проверяет revision/набор,
отвечает world_load_status `{revision,ready:true}`. Клиент разрешает управление
после этого ответа. Это подтверждение готовности рендера, не доказательство
правильности действий или основание назначить прогресс.

При смене interest сервер сразу отзывает право двигаться по удалённым участкам;
загрузка новых подтверждается заново. Пока ожидается подтверждение,
движение автомобиля допускается только внутри пересечения ранее подтверждённых
и всё ещё разрешённых участков с той же версией. Начальная позиция остаётся
на сервере, клиент показывает загрузку до первого подтверждения.

При сбое клиент отправляет world_load_failed с requestId:
`{revision,code:'BUDGET'|'FETCH'|'INVALID_DATA',chunkId:Id|null,message:string}`.
message — диагностический текст ≤500 символов, не команда серверу;
chunkId=null при проблеме всего набора. Сервер отвечает world_load_status
`{revision,ready:false}`. Устаревшая revision в обоих событиях отклоняется
через server_error STALE_WORLD_REVISION и не меняет актуальные разрешения.

После BUDGET сервер пересчитывает набор, уменьшает его без потери участка
текущей позиции и публикует новую revision; если даже минимальный набор
не помещается, возвращает WORLD_BUDGET_EXCEEDED и оставляет игрока
остановленным с видимой ошибкой, не подменяет данные пустой сценой.
После FETCH сервер один раз через 1 секунду публикует новую revision для
повторной попытки. При повторном сбое или INVALID_DATA автоматический цикл
прекращается: видимая ошибка, движение в незагруженную область запрещено,
пользователь может переподключиться после исправления сервера/данных.
Клиент не подтверждает частично загруженный набор как полностью готовый.

Метрика: dataBytes — точный размер UTF-8 JSON участка, который сервер
выдаёт по HTTP, до HTTP gzip. Сервер сериализует участок один раз при подготовке
мира и выдаёт неизменные байты данной версии. В JSON нет accountedBytes:
размер известен из ChunkRef заранее. Для файлов ресурсов byteLength — размер
исходного файла. totalWorldBytes — сумма реальных JSON всех участков плюс
**уникальных** файлов ресурсов всего мира, без фиктивного наполнителя.
Глобальный манифест учёта остаётся на сервере, участки выдаются по позиции.
Метаданные WorldMeta/WorldInterest также учитываются среди удерживаемых
данных мира: их UTF-8 JSON-размер входит в числитель; totalWorldBytes включает
размер соответствующего серверного глобального манифеста без двойного учёта.
Методика — предложение для согласования с трактовкой задания; она считает
уникальные данные, а не точную RAM/GPU-память и не удваивает JSON при parsing.

Порядок перехода:
1. Отменить старые загрузки, удалить ненужные участки и ссылки на их данные.
2. Посчитать уникальные сохранённые данные + метаданные + **резерв** всех
   входящих JSON и недостающих ресурсов. Общие ресурсы считать по `(id,version)` один раз.
3. До fetch проверить сумму ≤ min(cacheBudgetBytes, floor(totalWorldBytes×0.08)).
   Жёсткий потолок при любых переходах ≤10%. Сервер не разрешает набор,
   который минимально невозможно вместить. При нехватке не начинаем fetch,
   показываем ошибку и отправляем world_load_failed с code=BUDGET;
   сервер выполняет восстановление по правилам выше.
4. Загружать последовательно, проверять версию и фактический размер ответа
   против резерва. Превышающий заявленный размер поток прерывать до выхода
   за резерв (читать поток с лимитом, а не безусловный response.json()).
5. Устанавливать только ответы текущей revision; устаревшие игнорировать,
   освобождать их резерв после отмены/фактического завершения чтения.
6. При удалении последней ссылки вызывать dispose для геометрии/материалов/
   текстур, удалять JS-ссылки, object URL при наличии и обработчики.

HTTP мира/ресурсов: Cache-Control: no-store, клиент fetch cache:'no-store'.
Никаких Service Worker, CacheStorage, IndexedDB или сохранения старого мира.
Для максимальной предсказуемости MVP world HTTP выдаётся без gzip; различие
wireBytes/dataBytes при сжатии вводится только после согласования.
Сервер не меняет данные id/version на месте. Отказ по старому праву: 403,
клиент ждёт свежий interest, не загружает соседей наугад.
Диагностика: соединение, FPS, участки, retainedBytes, reservedBytes,
totalWorldBytes, доля (retained+reserved)/total, рабочий/жёсткий предел;
отдельно число геометрий/текстур. Размер файлов не называем GPU-памятью.

## 9. Демонстрационный сценарий: четыре задания

Источник уточнения — переписка команды 31.10.2026, 14:25–14:36.
П и К — **роли эпизода**, а не жёстко заданные аккаунты или номера ноутбуков.
Сервер привязывает роль к вошедшему userId и проверяет, что роль свободна.
Даша П и Даша К ездят с двух разных ноутбуков; третий браузер может наблюдать
как обычный игрок. Двух участниц не заменяем двумя окнами одиночной сцены.

### 9.1. Общий перекрёсток: задания 1 и 2

Нерегулируемый перекрёсток, главная соединяет юг и запад; север и восток —
**второстепенная дорога**, не прилегающая территория. Север = -Z, запад = -X.

```text
                   Второстепенная
                         ↓ К
                         |
Автобус → ---------------+--------------- Второстепенная
 Главная                 |
                         ↑ П
                       Главная
```

Траектории: П с юга поворачивает налево на запад; автобус с запада прямо на
восток; К с севера поворачивает налево на восток. Перед П «Главная дорога» с
табличкой направления; перед К «Уступите дорогу» с соответствующей табличкой.
Автобус тоже на главной. Рендер и сервер используют одни и те же пути/зоны.
Подвижный автобус — простая геометрия, серверная траектория и коллизии,
не ещё один реальный пользователь, не LLM-управляемый транспорт.

Подготовка: обе участницы подъезжают к своим контрольным точкам, останавливаются,
получают данные области и посылают episode_ready. Сервер проверяет позицию,
остановку, машину и world_loaded **обеих**, затем фиксирует сцену. Во время
выбора ответов автобус и две машины стоят. Персональные карточки выдаются
одновременно; одна участница не видит ответ другой и не отвечает за неё.

| № / scenarioId | Вопрос и варианты (стабильные answerId a1/a2/a3) | Правильный ответ на сервере | Источник и демонстрационная ошибка |
|---|---|---|---|
| 1 / `shared-priority-p` | «Кому Вы обязаны уступить дорогу при повороте налево?» a1 Только автобусу; a2 Только легковому автомобилю; a3 Никому | a3: П имеет приоритет перед автобусом, для которого находится справа, и перед К со второстепенной | На основе билета №1, вопроса №15; пункты 13.9–13.11. Ошибка: a1 |
| 2 / `shared-priority-k` | Тот же вопрос. a1 Только автобусу; a2 Только легковому автомобилю; a3 Обоим транспортным средствам | a3: К уступает обоим на главной независимо от их дальнейшего направления | На основе билета №16, вопроса №15; пункт 13.9. Ошибка: a1 |

Эти ответы — серверный контент, не часть task_started до ответа.
Подсказка П после a1: «Ты правильно заметила, что автобус тоже на главной.
Теперь сравним ваше положение: ты приближаешься к нему справа. Поэтому в этой
ситуации он уступает тебе». При повторном запросе — подсветка П, автобуса и
их траекторий с новым объяснением, а не повтор текста.
Подсказка К: «Поворот Даши П не отменяет её приоритет. Посмотри на табличку:
она подъехала по главной, а ты — по второстепенной. Сначала пропусти обоих».

После двух правильных ответов сервер переводит эпизод в практику:
**П → автобус → К**. П и К ведут сами, автобус движется по серверному пути.
Сервер проверяет завершение манёвра и освобождение конфликтной зоны прежде,
чем разрешает следующий проезд. Порядок — сценарная организация упражнения,
а не универсальное правило любого перекрёстка. На этапе карточек ввод
заморожен, на практике проверяется реальное действие. Ни клик «правильно»,
ни таймер не заменяют фактический проезд и освобождение зоны.

### 9.2. Отдельное задание 3: П, зелёный сигнал и пешеходы

scenarioId=`green-turn-pedestrians-p`. После общего эпизода П едет к
регулируемому перекрёстку: зелёный сигнал, поворот направо, пешеходы переходят
дорогу, на которую она поворачивает. Есть место безопасно уступить перед
переходом после въезда. Перед ответом состояние сцены фиксируется, чтобы
карточка не описывала исчезнувших пешеходов/другой сигнал.

Вопрос предлагает последовательность:
- a1: Дождаться прохода пешеходов перед стоп-линией.
- a2: Въехать на перекрёсток и уступить перед переходом.
- a3: Выполнить поворот, не останавливаясь.

Ответ по присланному сценарию билета — **a2**, на основе №37, вопроса №13,
пункт 13.1 ПДД. Демонстрационная ошибка — a3. Знак перехода объясняет:
«Зелёный разрешает тебе движение. При повороте твоя траектория пересекает путь
пешеходов — здесь нужно уступить им». Затем П исправляет ответ и выполняет
манёвр. Сервер проверяет пересечение траекторий, уступание и выход из зоны;
тему в блокнот добавляет только progress_updated после серверного результата.
Пешеходы и светофор движутся/переключаются сервером; на этапе практики зелёная
фаза сохраняется до безопасного завершения упражнения.

**Ответ a1 в карточке не превращаем автоматически в нарушение вождения.**
Безопасное ожидание перед стоп-линией само по себе не штрафуется; ошибку
выбора требуемой последовательности и фактическое неуступание разделяем.
Пока П решает и проходит упражнение, интерфейс и управление К не блокируются.

### 9.3. Отдельное задание 4: К, STOP без стоп-линии

scenarioId=`stop-no-line-k`. Другой перекрёсток, транспорта нет, STOP есть,
стоп-линии нет. До ответа показываются три учебные метки:
«Где Вы должны остановиться?»
- a1: Перед знаком — А.
- a2: Перед перекрёстком — Б.
- a3: Перед краем пересекаемой проезжей части — В.

Правильный ответ — **a3**, на основе билета №3, вопроса №2, правило знака 2.5
из приложения 1 к ПДД. Демонстрационная ошибка — a1. STOP отвечает:
«Обязательную остановку ты заметила правильно. Теперь выберем место:
стоп-линии здесь нет, поэтому остановиться нужно перед краем пересекаемой
проезжей части». Повторный вопрос подсвечивает границу В.

После исправления К останавливается в соответствующей зоне и продолжает
движение. Сервер проверяет полную остановку **до пересечения границы**:
speed ≤0.05 м/с непрерывно ≥0.5 с в зоне, фронт машины не за границей.
Это технический допуск симуляции, не утверждение обязательной длительности
остановки по ПДД. Остановка у А не заменяет остановку у В, но не является
сама по себе нарушением. Осмотр показан в демонстрации; движение головы
не оценивается как юридическое доказательство проверки безопасности.

### 9.5. Контракт общего эпизода, практики и подсветки

```ts
type EpisodeState = {
  episodeId: Id; scenarioId: 'shared-priority'; sceneRevision: number;
  phase: 'staging' | 'answering' | 'p_pass' | 'bus_pass' | 'k_pass' | 'completed' | 'paused' | 'cancelled';
  participants: {playerId:Id;role:'P'|'K';ready:boolean}[];
  selfRole: 'P' | 'K'; selfAnswerCorrect: boolean;
  activeDriver: 'P' | 'K' | 'bus' | null;
};
type PedestrianState = {id:Id;position:Vec3;yaw:number;moving:boolean};
type SignalState = {id:Id;aspect:'red'|'yellow'|'green'};
type VisualHint = {
  kind: 'highlight'; objectIds: Id[]; pathIds: Id[]; zoneIds: Id[];
  durationMs: number;
};
```

episode_join запрашивает свободную роль; сервер отвечает персональным
EpisodeState, не раскрывая выбранный ответ другой участницы.
phase/sceneRevision назначает сервер; клиент не меняет их сам.
sceneRevision обозначает зафиксированную постановку задачи и увеличивается
при её сбросе/изменении исходных условий, а не на каждом тике или фазе проезда.
У независимых заданий собственные scenarioId/sceneRevision; их изменения
не делают карточку другой участницы устаревшей.
После episode_ready сервер шлёт action_result и персональные episode_state;
при готовности обеих в первой попытке — task_started с разными
choice-taskId/scenarioId и общим sceneRevision. При повторе практики после
ошибки choice не повторяется: выдаются новые driving-taskId по правилам ниже. Повторная готовность идемпотентна. Менять роль можно только
через episode_leave и новый episode_join до answering.

Каждое из четырёх заданий состоит из двух серверных подзадач с разными taskId:
сначала kind=choice, затем kind=driving и options=[]. lessonId обозначает
соответствующее задание целиком. answer_submit содержит sceneRevision;
устаревшая карточка → STALE_SCENE, а не засчитанная ошибка ученицы.
Неверный ответ оставляет choice активным для исправления. После answer_result
с correct=false UI автоматически отправляет один npc_message назначенному
helperNpcId с taskId/sceneRevision и запросом объяснить ошибку; сервер берёт
выбранный ответ/правильность из своего состояния, не доверяя пересказу UI.
Повторный вопрос отправляет новый requestId. Ошибка LLM не блокирует исправление
ответа. Для разбора последней завершённой неуспешной попытки сервер также
принимает её taskId/sceneRevision от владельца; контекст берётся из сохранённой
попытки. После сброса такой ответ остаётся в истории диалога, а его старые
visualHints не накладываются на новую постановку. Текст prompt и sourceLabel — персональные поля карточки. Сервер выбирает
следующий taskId, не клиент. lesson.completed только после правильного ответа и фактического завершения
практики. В общем эпизоде окончательное completed для заданий 1/2 фиксируется
после успешного проезда всех троих и phase=completed; до этого проезд П —
промежуточный результат, который нельзя превратить в повторное начисление. nextTaskId=null завершает урок только
после driving; после correct choice сервер выдаёт driving task_started.
Для общего эпизода driving выдаётся после правильных ответов обеих;
карточка П до этого показывает «Ответ принят; ждём вторую участницу».

answer_result.stage различает choice/driving; mistakeKind=answer означает
ошибку карточки, driving — наблюдавшееся нарушение; null — успех.
Контролируемое ожидание не порождает answer_result с correct=false.
Для driving сервер выдаёт результат push без requestId. Для промежуточного
ожидания партнёра nextTaskId указывает серверный driving-task, но тот ещё
не активен до task_started. За повторную отправку/повторный snapshot
прогресс не начисляется. В счётчиках/памяти ошибки двух видов раздельны: Progress.mistakes содержит
записи по (topic,kind), а /api/v1/profile, /progress и progress_updated передают одинаковую
структуру; UI восстанавливает обе категории после нового входа.

После реального нарушения при практике сервер отправляет answer_result
stage=driving/correct=false/mistakeKind=driving, сохраняет ошибку и тормозит
учебный транспорт до безопасного состояния. Для общего эпизода phase=paused,
автобус и обе участницы не начинают новых манёвров; после освобождения зоны
сервер выполняет явно показанный UI учебный сброс на исходные контрольные
точки (не телепортирует транспорт сквозь движущихся участников), увеличивает
sceneRevision и возвращает staging. Оба прежних driving-taskId закрываются
как неуспешная/отменённая попытка; ошибка начисляется только фактическому
нарушителю. Правильные ответы choice сохраняются. После загрузки области
и новой episode_ready обеих выдаются новые driving-taskId, порядок снова
П → автобус → К. Начатые правильные действия не дают повторных наград.

Для отдельного задания 3/4 сброс касается только его участницы и NPC этой
сцены: безопасная остановка, возврат на свой checkpoint, новая sceneRevision
и новый driving-taskId; правильный choice не требуется повторять. nextTaskId
в результате ошибки указывает этот новый taskId; ввод включается после
нового task_started и готовности мира. Если безопасный сброс невозможен,
сцена остаётся paused с видимой причиной, без успеха/скрытого продолжения.
Заблокированный ввод до разрешённой фазы (например, К нажала газ в ожидании
автобуса) не считается сам по себе совершённым нарушением: оцениваем движение,
которое действительно произошло, а не нажатие клавиши.

Автобус передаётся в vehicles: variant='bus', controller='npc', driverId=null;
игроки не могут им управлять. Игровые машины controller='player'.
Snapshot несёт pedestrians/signals текущей области; пустые списки — [] и
полностью заменяют прежний набор. NPC-пешеходы и автобус не зависят от FPS клиента.
Позиции транспорта и пешеходов видны всем наблюдателям, текст карточек,
выбор ответа и память — только владельцу. Общая остановка распространяется
лишь на участников/автобус этого эпизода; посторонние игроки управляют собой,
но серверные коллизии и запрет вмешиваться в защищённую учебную зону сохраняются.

visualHints приходит в npc_reply вместе с taskId/sceneRevision. Аня выбирает
подсказку из разрешённых объектов/путей/границ сценария после повторного вопроса;
LLM не изобретает координаты или objectId. Клиент подсвечивает только загруженные
id текущей сцены, не подгружает весь мир ради подсказки и не меняет приоритет.
Незнакомый id пропускается с диагностикой; устаревший taskId/revision не меняет
текущую сцену. Подсветка есть дополнение к тексту, а не замена серверной проверки.

При потере участницы общий эпизод переходит в paused, новые старты манёвров
запрещены, автобус безопасно тормозит; начатый манёвр завершается/останавливается
без столкновения под контролем сервера. После восстановления сервер через
world_joined возвращает EpisodeState и activeTask; загрузка области и повторная
готовность обеих нужны перед продолжением. Не начисляем успех за отключение.
episode_leave отменяет общий эпизод без успеха: сервер отправляет обеим
персональный episode_state с phase=cancelled, снимает обе активные карточки,
после безопасной остановки возвращает свободное движение. В последующих
world_joined episode=null и activeTask=null; сохранённые попытки остаются в памяти. Самостоятельные задания 3/4 доступны
через lesson_start без второго игрока — это позволяет проверить localhost
при выключенном Wi-Fi, не изображая успешное прохождение общего эпизода.

### 9.6. Локальная LLM, RAG и серверная логика

По уточнению Ани: **RAG + БД/JSON**, отдельный backend со всей игровой логикой,
карта на фронте, кеширование, WS и мультиплеер.
Распределение данных:
- PostgreSQL: аккаунты/сессии, роль и состояние эпизода, прогресс, история ошибок,
  память (userId,npcId), использованные примеры и краткое резюме.
- Серверные JSON: сцены, правильные answerId, предикаты проезда, источники ПДД,
  подготовленные объяснения/альтернативы, RAG-фрагменты и разрешённые подсветки.
- Клиент: только ближайшие участки, видимые сущности, персональная карточка и UI.
  «Карта на фронте» означает рендер, а не включение полного города в bundle.

Сервер получает answer_submit → детерминированно проверяет → сохраняет
результат/ошибку → отправляет answer_result. **Этот обработчик сам LLM не
вызывает.** После ошибки UI отправляет один npc_message (§9.5), либо ученица
задаёт вопрос вручную. Только обработчик npc_message извлекает релевантные
локальные фрагменты ПДД/сценария (RAG), добавляет личную память, факт ошибки
и характер знака, вызывает **локальную** LLM, проверяет результат и отправляет
npc_reply с requestId именно этого npc_message. npc_typing использует тот же
requestId. Один requestId не запускает вторую генерацию; повторный вопрос —
новая операция. Поэтому один неверный ответ не создаёт два конкурирующих
LLM-запроса от сервера и UI. Ни retrieval, ни модель не обращаются в облако.
Векторная БД не обязательна: способ локального поиска выбирает Аня; важно
проверяемое извлечение нужных фрагментов, а не отправка всей базы модели.
RAG не даёт модели права менять правильный ответ, начислять прогресс,
выдумывать правило или публиковать ответ другой ученицы.

После повторного вопроса backend выбирает иной exampleId/visualHints;
при освоенной теме вводная не повторяется без запроса. Неизвестный вопрос →
уточнение. При недоступной LLM — AGENT_UNAVAILABLE и видимое состояние ошибки;
детерминированные задания продолжают работать, но это не засчитывается как
демонстрация работающего LLM-помощника. Подготовленный текст не выдаём за
сгенерированный: generation='local_llm' допускается только после реального вызова.
LLM объясняет на основе условий, извлечённых пунктов ПДД и памяти; ожидаемые
реплики в §9.1–9.3 — ориентиры смысла, не обязательное дословное повторение.

Аня сохраняет позицию и машину каждые ≤5 секунд и при корректном выходе;
прогресс, состояние эпизода и память — транзакционно после значимых событий.
При восстановлении проверяет занятость машины и безопасную позицию.
Допускается потеря последних ≤5 секунд движения при аварии, не сохранённого
результата задания. Перезапуск сервера не стирает аккаунты и память.
